# 저자권 원장 — 기여 측정과 참여 유도 규약

> 다음 프로젝트 킥오프에서 **착수 전에** 합의하는 문서. 끝나고 나서 기여를 소급 판정하면 반드시 다툼이 생긴다.
> 작성 2026-08-14 (BIOP01/BIOP02 운영 경험에서 도출). 특정인 평가가 아니라 일반 규칙이다.

## 왜 필요한가

기여를 나중에 재면 **기록이 남은 것만** 세게 된다. 커밋 수는 ID를 여러 개 쓰면 틀리고, 댓글 글자 수는 말이 많은 쪽이 이기고, "원고에 도달한 변경"은 같은 문단을 세 번 고쳐도 세 건으로 잡힌다. 그래서 무엇을 셀지 **먼저** 정하고, 세는 방법까지 함께 적어 둔다.

## 원칙 세 가지

1. **지표는 판정이 아니라 근거다.** 순위는 사람이 정하고 전원이 합의한다. 숫자는 그 대화의 입력값일 뿐이다.
2. **저자 포함 여부의 게이트는 ICMJE 4항이지 지표가 아니다.** 지표는 이미 저자인 사람들의 순서를 논의할 때만 쓴다.
3. **모든 대리지표는 틀린다.** 각 축마다 "이 지표가 놓치는 것"을 함께 적었다. 그 칸을 읽지 않고 숫자만 쓰면 안 된다.

---

## 측정하는 여섯 가지

축에 번호를 붙이지 않는다. 순서가 아니라 병렬이고, 프로젝트 성격에 따라 가중치가 달라진다.

### 발제 — 일을 스스로 만들어 냈는가

**대리지표:** 티켓 생성 수 + **무주(無主) 작업 자가배정 수** + 지시받지 않은 범위 확장.

```bash
# 티켓 생성자 분포
curl -sG ".../rest/api/3/search/jql" --data-urlencode "jql=project = <KEY>" \
  --data-urlencode "fields=key,creator" --data-urlencode "maxResults=200" \
  | python3 -c "import json,sys;from collections import Counter; \
    d=json.load(sys.stdin); \
    print(Counter(i['fields']['creator']['displayName'] for i in d['issues']).most_common())"
```

**놓치는 것:** 티켓 생성만 세면 **조용히 챙기는 사람이 0점으로 나온다.** 담당 없이 떠 있는 일을 가져가거나, 티켓에 적힌 범위보다 넓게 본 사람은 생성 카운트에 안 잡힌다. 자가배정과 범위 확장을 반드시 함께 본다. 실제로 이 항목 하나로 평가가 뒤집힌 사례가 있었다.

### 착지 — 산출물이 정본에 닿았는가

**대리지표:** 원고·results 등 **정본 파일에 도달한 변경을 claim 단위로** 센다. 커밋 수도 줄 수도 아니다.

**세는 법:** "이 변경으로 논문의 어떤 주장이 생겼거나, 바뀌었거나, 방어됐는가"를 한 줄로 쓸 수 있으면 1건. 못 쓰면 0건이다.

**놓치는 것:** 같은 초록 문단을 세 번 깎으면 커밋 3건·변경 24줄이지만 claim 기준으로는 **1건**이다. 반대로 두 줄짜리 수정이 논문의 핵심 캐비엇과 정면으로 어긋난 문장을 잡아낸 것이라면 그건 온전한 1건이다. 줄 수로 세면 둘 다 틀린다.

### 발안 대 실행 — 아이디어가 누구 것인가

**대리지표:** 커밋 메시지와 댓글에 **발안자와 그 발안의 위치**를 명시한다. 티켓 설명란에 설계가 적혀 있으면 그 날짜가 설계 귀속의 근거가 된다.

**놓치는 것:** 이걸 강제하지 않으면 **실행자에게 설계 지분까지 계상되고 발안자는 기록에서 지워진다.** 남의 리뷰 제안을 구현한 커밋은 그 사실을 커밋 메시지에 적는다. 티켓을 만들 때 방법을 적어 두면, 나중에 다른 사람이 실행해도 설계 귀속이 유지된다.

### 자립 — 산출 하나에 남의 시간이 얼마나 들었는가

**대리지표:** 산출 1건당 타인 지원 요청의 횟수와 규모. 데이터 준비, 환경 셋업, 경로 디버깅, 권한 처리를 모두 센다.

**놓치는 것:** 이 축을 안 보면 **순기여가 음수인 작업이 양수로 잡힌다.** 결과물만 보면 기여지만, 그걸 만들기 위해 남이 4GB를 두 번 복사하고 실패를 디버깅해 줬다면 팀 전체로는 손해일 수 있다. 지원이 나쁘다는 뜻이 아니라, 지원 비용을 기여 계산에 넣으라는 뜻이다.

### 응답 — 요청에 얼마나 빨리 붙는가

**대리지표:** 멘션·요청 → **실질 회신**까지의 중앙값 시간. 마감이 걸린 요청은 별도로 본다.

**놓치는 것:** "확인했습니다"는 실질 회신이 아니다. 판단·수치·결정이 담겨야 센다. 그리고 응답이 느린 것과 바쁜 것은 다르므로, **못 하겠으면 빨리 말하는 것**도 좋은 응답으로 친다.

### 검토 실효 — 남의 산출물에서 진짜 결함을 잡았는가

**대리지표:** 지적 건수가 아니라 **실제로 고쳐진 지적의 건수**. 반려된 지적은 세지 않는다.

**놓치는 것:** 건수만 세면 트집이 이긴다. 반대로 "이대로 좋다"는 판정도 검토 노동이므로, 고칠 게 없었던 검토는 0이 아니라 별도로 기록한다.

## 참여 유도 — 킥오프에서 미리 정하는 여섯 가지

### 조건은 "무엇이 생기면"이 아니라 "무엇을 하면"으로 쓴다

기여 재검토 조건을 열 때 "실질 기여가 생기면 재검토하겠다"처럼 쓰면, 이미 설계된 일을 실행만 해도 조건이 충족됐다고 주장할 여지가 생긴다. **"이 티켓의 X를 설계부터 해서 결과까지 내면"** 처럼 범위를 못박는다.

### 티켓 설명란에 설계와 날짜를 박는다

방법·판정 기준·비용 판단을 티켓에 적어 두면, 나중에 누가 실행하든 설계 귀속이 기록으로 남는다. 이게 없으면 실행자의 기억과 발제자의 기억이 갈린다.

### 배정할 때 자립 조건을 함께 쓴다

입력 데이터·환경·권한은 원칙적으로 수행자가 준비한다. 지원이 필요하면 **착수 전에 한 번에** 요청한다. 진행 중에 나눠서 요청하면 지원자의 컨텍스트 전환 비용이 크다.

### 커밋 메시지에 발안자를 쓴다

남의 제안을 구현한 커밋은 그 사실과 출처를 적는다. 이건 예의가 아니라 기록이다.

### 기여 재검토는 정기 창구로만 연다

월 1회처럼 정해진 시점에 전원 대상으로 연다. 개별 협상으로 열면 **말을 꺼낸 사람만 재평가받는** 구조가 되고, 조용히 일한 사람이 불리해진다.

### 무주 작업 목록을 공개한다

담당 없는 일을 모아 보이게 두면 자가배정이 실제로 일어난다. 이건 검증된 방법이다 — 목록에 떠 있던 일을 스스로 가져가 티켓 범위보다 넓게 처리한 사례가 있었다.

## 킥오프 체크리스트

착수 전에 아래를 문서로 합의하고 티켓에 남긴다.

- [ ] 저자 포함 기준 = ICMJE 4항. 4항을 못 채우면 Acknowledgements로 간다는 것을 미리 말한다.
- [ ] 위 여섯 축 중 **이 프로젝트에서 무겁게 볼 축**을 고른다. 전부 같은 무게로 두지 않는다.
- [ ] 순서 결정 시점을 정한다(예: 투고 전 1회). 그전까지 순서는 "제안"으로만 표기한다.
- [ ] 기여 재검토 창구의 주기와 형식을 정한다.
- [ ] 티켓 생성·자가배정 권한을 전원에게 연다.
- [ ] git 저자 ID를 사람당 하나로 통일하거나, 여러 개면 **매핑 표를 먼저 만든다**.

## 집계할 때 반드시 하는 것

**git 저자 ID를 병합하고 세라.** 한 사람이 회사 메일, 개인 메일, GitHub noreply를 섞어 쓴다. 병합 전 카운트는 그냥 틀린 숫자다.

```bash
git log --all --format='%an|%ae' | sort -u   # 먼저 이걸로 매핑 표를 만든다
```

**댓글 수·글자 수는 volume proxy다.** ICMJE 기준이 아니다. 순위 근거로 단독 사용하지 않는다.

## 이 지표가 못 재는 것

착상, 방향 전환의 판단, 틀린 길을 일찍 접게 만든 한마디, 남이 포기하려 할 때 붙잡아 준 것. 전부 논문의 질을 좌우하지만 기록에 안 남는다. 그래서 마지막 결정은 지표가 아니라 **같이 일한 사람들의 합의**다. 이 문서는 그 합의를 감정이 아니라 기록 위에서 하자는 장치일 뿐이다.
